# 09. 데이터 모델 확정 (1차 오픈)

2단계 솔루션 아키텍트 산출물 | 2026-07-31
`03-데이터모델-초안.md`를 **실데이터 검증 후 확정**한 것. 이 문서가 기준이다.

> 확정 근거: 상품 10,691건 / 연락처 2,603건 / 차량 2,574건 / 서비스 69건 실물 분석 완료

---

## 1. 전체 구조

```
app_user ─────────────────────────┐ (누가 했는지 기록)
                                  │
vehicle_maker ── vehicle ── customer
    (정규화)        │           │
                    │           └── quote ── quote_item
brand ──── product ─────┬── stock_item ── stock_movement
                        └── price_rule
service_item ───────────────────── quote_item
```

**1차 오픈 테이블 12개.** 이보다 적으면 기능이 안 나오고, 많으면 4주에 못 만든다.

---

## 2. 공통 규칙

| 규칙 | 내용 |
|---|---|
| PK | `bigserial` (단순·빠름). 외부 노출 번호는 별도 컬럼 |
| 시각 | 전부 `timestamptz`, 저장은 UTC, 표시는 KST |
| 삭제 | **하지 않는다.** `is_active` 또는 `status` 변경 |
| 생성 이력 | 모든 테이블에 `created_at`, `created_by`, `updated_at` |
| MARS 코드 | 우리가 만들지 않고 **MARS 값을 그대로 보조키로 보관** |
| 금액 | `integer` (원 단위. 소수점 없음) |
| 비율 | `numeric(5,4)` — `0.2500` = 25% |

## 3. 테이블 정의

### 3-1. `app_user` — 직원

```sql
CREATE TABLE app_user (
  id            bigserial PRIMARY KEY,
  login_id      text UNIQUE NOT NULL,
  password_hash text NOT NULL,
  pin_hash      text,                          -- 4자리 PIN (기기 전환용)
  name          text NOT NULL,
  role          text NOT NULL                  -- 'owner' | 'tech'
                CHECK (role IN ('owner','tech')),
  is_active     boolean NOT NULL DEFAULT true,
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

> `role='tech'`에게는 **매입원가·마진 컬럼을 서버 응답에서 제외**한다 (`08` 3장).

---

### 3-2. `brand` — 타이어 브랜드

MARS 제조사 코드 18종을 그대로 쓴다.

```sql
CREATE TABLE brand (
  code        text PRIMARY KEY,     -- 'MI','PI','HK','CO','KM','NX','BS','GY' ...
  name_ko     text NOT NULL,        -- '미쉐린','피렐리','한국타이어' ...
  name_en     text,
  sort_order  integer DEFAULT 999   -- 자주 파는 브랜드를 위로
);
```

---

### 3-3. `vehicle_maker` — 차량 제조사 (⭐ 정규화 필수)

실데이터에 **48종으로 흩어져 있다** (`현대자동차` 956 / `현대` 53 / `HYUNDAI` 17).
통합하지 않으면 "현대"로 검색했을 때 절반이 안 나온다.

```sql
CREATE TABLE vehicle_maker (
  code        text PRIMARY KEY,     -- 'HYUNDAI','KIA','GENESIS','BENZ' ...
  name_ko     text NOT NULL,        -- '현대'
  is_imported boolean NOT NULL,     -- ⭐ 국산/수입 → 공임이 갈린다
  sort_order  integer DEFAULT 999
);

-- MARS 원본 표기 → 정규화 코드 매핑
CREATE TABLE vehicle_maker_alias (
  raw_name  text PRIMARY KEY,       -- '현대자동차','현대','HYUNDAI'
  code      text NOT NULL REFERENCES vehicle_maker(code)
);
```

> ⭐ **`is_imported`가 견적 금액을 바꾼다.** 얼라인먼트 60,000(국산) vs 80,000(수입),
> 엔진오일 30,000 vs 50,000. 차량을 고르면 공임이 자동으로 정해진다.

### 3-4. `product` — 상품 마스터 *(D-12 반영해 일반화)*

부품 265종이 들어오므로 **타이어 전용이 아니다.**

```sql
CREATE TABLE product (
  id             bigserial PRIMARY KEY,
  mars_item_no   text UNIQUE,              -- '178959' MARS 품번 (타이어는 100% 있음)
  item_type      text NOT NULL             -- ⭐ 'tire' | 'part'
                 CHECK (item_type IN ('tire','part')),
  is_serialized  boolean NOT NULL,         -- ⭐ 타이어=true(1본1행), 부품=false(수량관리)

  brand_code     text REFERENCES brand(code),
  pattern        text,                     -- 'CROSSCLIMATE 2'
  raw_name       text NOT NULL,            -- 원문 보존 (재파싱 대비)

  -- 타이어 전용 (부품은 전부 NULL)
  width          integer,                  -- 225
  aspect_ratio   integer,                  -- 45
  rim_inch       numeric(4,1),             -- 17  (17.5 대비)
  load_index     text,                     -- '94'
  speed_rating   text,                     -- 'W'
  season         text,                     -- '사계절'|'여름'|'겨울'|NULL

  -- 부품 전용 (타이어는 전부 NULL)
  part_no        text,                     -- ⭐ 'MBA-039','SM188' 공급사·제조사 품번
  fitment        text,                     -- ⭐ '제네시스 DH / 펠리세이드' 적용 차종
  position       text,                     -- '앞'|'뒤' (브레이크패드)

  category       text,                     -- '10-TIRES','40-BATTERY' ...
  barcode        text,                     -- 제조사 바코드 (중복 가능 — SKU 단위)
  list_price     integer,                  -- ⭐ 기표가 (MARS 단가1). 부품은 미확보
  purchase_price integer,                  -- 부품 매입가 (미확보 — 미결)
  supplier_code  text,                     -- 'V001/00010'

  spec_parsed    boolean NOT NULL DEFAULT false,
  stock_tracked  boolean NOT NULL DEFAULT false,  -- ⭐ 한 번이라도 입고된 적이 있는가
  is_active      boolean NOT NULL DEFAULT true,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_product_spec    ON product(rim_inch, width, aspect_ratio)
                                 WHERE is_active AND item_type='tire';
CREATE INDEX idx_product_brand   ON product(brand_code) WHERE is_active;
CREATE INDEX idx_product_barcode ON product(barcode) WHERE barcode IS NOT NULL;
-- ⭐ 부품 검색의 전부: 적용 차종 부분검색
CREATE INDEX idx_product_fitment ON product USING gin (fitment gin_trgm_ops);
CREATE INDEX idx_product_partno  ON product(part_no) WHERE part_no IS NOT NULL;
```

> **검색 축이 둘이다.** 타이어는 **규격**(225/45R17)으로, 부품은 **적용 차종**으로 찾는다.
> 차량을 이미 조회한 상태(화면 2)라면 **그 차에 맞는 부품만 자동으로 걸러줄 수 있다.**

> `spec_parsed = false`인 **101건**만 1주차에 사람이 보정한다 (타이어 전체의 1.0%).
> `raw_name`을 남겨두므로 언제든 다시 파싱할 수 있다.

#### ⭐ `stock_tracked` — 「없다」와 「모른다」를 구분한다

오픈 시점에 재고를 신뢰할 수 있는 것은 **미쉐린 타이어뿐**이다. 한국·금호·넥센 등은
실제로는 매장에 있지만 **시스템에는 아직 없다.** 프로그램이 돌아가는 것을 확인한 뒤
재고 등록·수정 기능으로 직접 넣을 예정이다 *(사장님 확인, 2026-08-01)*.

이때 상품 마스터에는 10,691건이 다 있으므로, 아무 처리도 안 하면 화면은
**「한국 K127 — 재고 0본」**이라고 말한다. 이건 **거짓말이다.** 창고에 있다.

| `stock_tracked` | 재고 수 | 화면 표시 | 의미 |
|---|---|---|---|
| `true` | 4 | 🟢 **4본** | 있다 |
| `true` | 0 | 🔴 **0본 (소진)** | 정말 없다 — 주문해야 한다 |
| `false` | 0 | ⚪ **미등록** | **모른다. 창고를 봐야 한다** |

- 최초 입고가 확정되는 순간 `stock_tracked = true`가 되고, 그 뒤로는 숫자를 믿는다.
- 미쉐린 57종은 1주차 이관 시점에 곧바로 `true`.
- 나머지는 `false`로 시작해 **사장님이 넣는 만큼 하나씩 켜진다.**

> 부품의 `verified_at IS NULL → 미확인`과 **같은 원리**다.
> 모르는 것을 0이라고 말하면 정비사는 시스템을 한 번 보고 다시는 안 본다.

### 3-5. `stock_item` — 재고 *(D-12 반영: 타이어와 부품을 한 테이블로)*

```sql
CREATE TABLE stock_item (
  id           bigserial PRIMARY KEY,
  stock_no     text UNIQUE NOT NULL,       -- 시스템 자동 채번 'S26-000001'
  product_id   bigint NOT NULL REFERENCES product(id),
  qty          integer NOT NULL DEFAULT 1, -- ⭐ 타이어=항상 1 / 부품=보유 수량
  status       text NOT NULL DEFAULT '재고'
               CHECK (status IN ('재고','보관중','판매완료','반품','폐기')),
  dot          text,                       -- ⭐ 제조주차 'WWYY' (1826 = 18주 2026년)
  purchase_price integer,                  -- 실매입가 (알면 우선 사용)
  location     text,                       -- 창고 위치 (1층/2층? — 미확인)
  received_at  timestamptz NOT NULL DEFAULT now(),
  sold_at      timestamptz,
  quote_id     bigint,                     -- 판매된 견적
  verified_at  timestamptz,                -- ⭐ NULL이면 화면에 '미확인' 표시
  verified_by  bigint REFERENCES app_user(id),
  created_by   bigint REFERENCES app_user(id),
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_stock_avail ON stock_item(product_id) WHERE status = '재고';
CREATE INDEX idx_stock_dot   ON stock_item(dot) WHERE status = '재고' AND dot IS NOT NULL;
```

**두 가지 운영 방식이 한 테이블에 공존한다:**

| 상품 | `is_serialized` | 저장 방식 | 이관 시 `verified_at` |
|---|---|---|---|
| 타이어 (미쉐린) | `true` | **1본 = 1행**, `qty`=1, `dot` 보유 | ✅ **채움** (실사 데이터) |
| 부품 | `false` | **1행에 수량**, `qty` 증감 | ❌ **비움** → `미확인` |

> 테이블을 둘로 쪼개지 않는 이유: **재고 현황·출고 화면을 하나로 유지**하는 게 현장에 낫다.
> 정비사가 "타이어 재고"와 "부품 재고"를 다른 메뉴에서 찾게 만들 이유가 없다.

### ⭐ `verified_at` — 모르는 것을 아는 척하지 않는다

부품 재고 수량은 실물과 맞지 않는다 (사장님 확인, D-12 5번).

```
verified_at IS NULL  →  화면에 숫자 대신 「미확인」 + [지금 세기] 버튼
verified_at 있음     →  「5개  ✅ 7/31 확인」
```

**왜 0으로 넣지 않는가**: 출고할 때마다 "재고 없음"이 떠서 정비사가 시스템을 우회하게 된다.
**왜 엑셀 숫자를 넣지 않는가**: 한 번 틀린 숫자를 보면 그다음부터 아무도 안 믿는다.

> 자주 나가는 부품 20~30종부터 자연스럽게 확정된다.
> **D-05(할인율)·D-02(DOT)와 같은 철학** — 미리 다 채우지 않고 쓰면서 정확해지게 한다.

**타이어 입고 흐름** (바코드는 SKU 단위라 개별 본을 구분하지 못한다 — D-02):
```
스캔 → 상품 인식 → DOT별 수량 입력 → 그 수량만큼 행 자동 생성 + stock_no 채번
       예: DOT 1826 / 14본  →  14행 생성 (전부 dot='1826')
```
출고 시에는 그 상품의 `재고` 행 중 **DOT가 오래된 것부터** 뺀다(선입선출).
DOT가 없는 행은 `received_at` 순서로 뺀다.

> ⭐ **`dot` 인덱스로 재고 노후화 경고가 나온다.**
> 실데이터 기준 2024년산 5본 / 2025년 89본 / 2026년 202본 — 오래된 것부터 팔아야 한다.

### 3-6. `stock_movement` — 입출고 이력

```sql
CREATE TABLE stock_movement (
  id            bigserial PRIMARY KEY,
  stock_item_id bigint NOT NULL REFERENCES stock_item(id),
  type          text NOT NULL
                CHECK (type IN ('입고','출고','조정','반품')),
  reason        text,                      -- '판매','보관','폐기','실사조정'
  quote_id      bigint,
  memo          text,
  created_by    bigint REFERENCES app_user(id),
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

> 재고가 실물과 어긋났을 때 **"언제 누가 무엇을 했는지"** 를 되짚을 수 있어야 한다.
> 이 테이블이 없으면 원인을 영원히 못 찾는다.

### 3-7. `customer` — 고객 ⭐ (MARS 「연락처」)

```sql
CREATE TABLE customer (
  id              bigserial PRIMARY KEY,
  mars_contact_no text UNIQUE,             -- ⭐ 'C583-012670' (D583 아님! D-10)
  name            text NOT NULL,           -- 원문 보존 '고태환[한진택배]'
  name_search     text,                    -- 검색용 정규화 (괄호 제거·공백 제거)
  memo            text,                    -- 괄호 안 내용 복사 '한진택배'
  phone           text,                    -- 실데이터 99.6% 보유
  type            text NOT NULL DEFAULT '개인'
                  CHECK (type IN ('개인','법인')),
  grade           text,                    -- 우리가 만드는 축 (MARS엔 없음)
  extra_discount_rate numeric(5,4),        -- 등급별 추가 할인
  family_group_id bigint,                  -- 같은 전화 쓰는 묶음 (병합 아님)
  is_active       boolean NOT NULL DEFAULT true,
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_customer_phone ON customer(phone);
CREATE INDEX idx_customer_name  ON customer USING gin (name_search gin_trgm_ops);
```

> ❌ **`email` 컬럼 없음.** 실데이터 0건이다. 알림은 문자 단일 경로.
> ⚠️ **`name`은 절대 정리하지 않는다.** `고태환[한진택배]`는 사장님이 손님을 기억하는 방식이다.
>    검색은 `name`·`name_search`·`memo`를 **전부** 뒤진다. (D-10)

**`family_group_id`가 필요한 이유**: 같은 전화번호에 다른 이름이 72그룹 있다.
`['(주)서용엔지니어링(수자원삼촌)', '서용ENG', '수자원공사']` — **합치면 안 되지만
연결은 보여야 한다.** 한 명을 찾으면 "같은 번호 사용" 표시가 뜬다.

### 3-8. `vehicle` — 차량

```sql
CREATE TABLE vehicle (
  id            bigserial PRIMARY KEY,
  mars_vehicle_no text UNIQUE,             -- 'V583-000001'
  customer_id   bigint NOT NULL REFERENCES customer(id),
  plate_no      text NOT NULL,             -- 원문 '12가3456'
  plate_no_norm text NOT NULL,             -- 정규화 (공백·하이픈 제거)
  maker_code    text REFERENCES vehicle_maker(code),
  model         text,                      -- 'GRANDEUR'
  year          integer,                   -- 2008 (MARS 등록날짜에서 추출)
  mileage       integer,
  mileage_at    timestamptz,
  last_fitted_size text,                   -- '225/45R17' 판매 시 자동 기록
  last_visit_at timestamptz,
  memo          text,
  is_active     boolean NOT NULL DEFAULT true,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_vehicle_plate ON vehicle(plate_no_norm);
CREATE INDEX idx_vehicle_plate_tail ON vehicle(right(plate_no_norm, 4));
```

> ⭐ **뒷 4자리 인덱스**를 따로 둔다. 고객은 "3456이요"라고 말한다.
> 앞자리를 다 기억하는 사람은 드물다. **뒷자리 검색이 실제로 더 자주 쓰인다.**

> 순정규격(`oem_tire_size`)은 **두지 않는다.** MARS에도 없고 외부 API도 안 쓴다(D-04).
> 대신 `last_fitted_size`가 판매할 때마다 자동으로 쌓인다 — 현장에서 더 유용하다.

### 3-9. `service_item` — 서비스·공임 ⭐ (1주차로 앞당김)

MARS 「패스트핏 서비스 목록」 69건을 이관한다.

```sql
CREATE TABLE service_item (
  id              bigserial PRIMARY KEY,
  mars_service_no text UNIQUE,             -- 'S001/1180'
  name            text NOT NULL,           -- '휠타이어 교환 - 17인치 이하'
  short_name      text,                    -- '장착' (버튼에 쓸 짧은 이름)
  price           integer,                 -- 공임. 3건은 NULL → 건별 입력
  category        text,                    -- '90-SERVICE'

  -- ⭐ 자동 계산 규칙 (이게 없으면 매번 사람이 틀린다)
  qty_rule        text NOT NULL DEFAULT 'per_job'
                  CHECK (qty_rule IN ('per_unit','per_2_units','per_job')),
  rim_min         numeric(4,1),            -- 인치 구간 하한
  rim_max         numeric(4,1),            -- 인치 구간 상한
  for_imported    boolean,                 -- NULL=공통, true=수입, false=국산

  is_tire_related boolean NOT NULL DEFAULT false,  -- 타이어 견적에 자동 제안
  auto_suggest    boolean NOT NULL DEFAULT false,  -- 기본 체크 상태로 뜸
  is_favorite     boolean NOT NULL DEFAULT false,  -- 버튼으로 노출
  is_active       boolean NOT NULL DEFAULT true
);
```

**실데이터 매핑 예:**

| MARS 서비스 | `qty_rule` | `rim_min~max` | `for_imported` | `auto_suggest` |
|---|---|---|---|---|
| 휠타이어 교환 17인치 이하 | `per_unit` | ~17 | — | ✅ |
| 휠타이어 교환 18인치 이상 | `per_unit` | 18~20.9 | — | ✅ |
| 휠타이어 교환 21인치 이상 | `per_unit` | 21~ | — | ✅ |
| 휠밸런스 2개당 17인치 이하 | **`per_2_units`** | ~17 | — | ✅ |
| 휠밸런스 2개당 20인치 이하 | **`per_2_units`** | 17.1~20 | — | ✅ |
| 휠밸런스 2개당 21인치 이상 | **`per_2_units`** | 21~ | — | ✅ |
| 휠얼라인먼트 국산 승용 | `per_job` | — | `false` | ❌ |
| 휠얼라인먼트 수입 승용 | `per_job` | — | `true` | ❌ |

> ⚠️ **인치 구간이 교환(17/18/21)과 밸런스(17/20/21)로 다르다.**
> 20인치 타이어 → 교환은 "18인치 이상", 밸런스는 "20인치 이하"에 걸린다.
> **사람이 고르면 반드시 틀린다.** 규격에서 자동 판정해야 하는 이유다.

> ⚠️ **`per_2_units`**: 4본 교체 시 수량 = ⌈4÷2⌉ = **2**.
> 이 규칙이 없으면 휠밸런스를 **매번 절반만 청구**하게 된다.

### 3-10. `price_rule` — 할인율 규칙 (D-05)

```sql
CREATE TABLE price_rule (
  id          bigserial PRIMARY KEY,
  scope       text NOT NULL
              CHECK (scope IN ('item','pattern','brand','category')),
  target      text NOT NULL,               -- '000425' | 'PILOT SPORT 4 S' | 'MI'
  supplier_code text,                      -- 매입처별로 다르면 사용 (미확인 사항)
  purchase_discount_rate numeric(5,4),     -- 매입 할인율 (nullable)
  sales_discount_rate    numeric(5,4),     -- 판매 할인율 (nullable)
  priority    integer NOT NULL,            -- 1=item 2=pattern 3=brand 4=category
  updated_by  bigint REFERENCES app_user(id),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (scope, target, supplier_code)
);
```

**적용 로직 (좁은 것이 이긴다):**
```sql
SELECT * FROM price_rule
WHERE (scope='item'     AND target = :mars_item_no)
   OR (scope='pattern'  AND target = :pattern)
   OR (scope='brand'    AND target = :brand_code)
   OR (scope='category' AND target = :category)
ORDER BY priority LIMIT 1;
```

> **처음엔 이 테이블이 비어 있다.** 팔면서 채워진다 (D-05).
> 값이 없으면 화면에 "⚠ 미설정"이 뜨고, 그 자리에서 입력하면 저장 범위를 물어본다.

### 3-11. `quote` / `quote_item` — 견적

```sql
CREATE TABLE quote (
  id           bigserial PRIMARY KEY,

  total_amount integer NOT NULL DEFAULT 0,

  -- MARS 연동 공통 필드 (모든 거래성 테이블 공통)
  mars_status  text NOT NULL DEFAULT '미전송'
               CHECK (mars_status IN ('미전송','전송완료','보류','해당없음')),
  mars_synced_at timestamptz,
  mars_ref_no  text,                       -- MARS 매출주문/송장 번호
  mars_memo    text,

  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_quote_mars ON quote(mars_status, created_at)
                            WHERE mars_status = '미전송';
```

> `idx_quote_mars`가 **MARS 입력 대기열 화면 그 자체**다.
> 3일 경과 경고도 이 인덱스로 즉시 뽑힌다.

```sql
CREATE TABLE quote_item (
  id            bigserial PRIMARY KEY,
  quote_id      bigint NOT NULL REFERENCES quote(id) ON DELETE CASCADE,
  line_type     text NOT NULL CHECK (line_type IN ('tire','service','custom')),

  product_id      bigint REFERENCES product(id)      ,
  service_item_id bigint REFERENCES service_item(id),
  description   text NOT NULL,             -- 화면 표시용 (스냅샷)
  qty           integer NOT NULL DEFAULT 1,

  -- 계산 과정 전부 보존 (최종가만 남기면 마진 분석을 못 한다)
  list_price    integer,                   -- 기표가 스냅샷
  purchase_discount_rate numeric(5,4),
  purchase_cost integer,                   -- 매입원가 (owner 전용)
  sales_discount_rate    numeric(5,4),
  applied_rule_scope text,                 -- 'item'|'brand'|'수동입력'
  customer_discount_rate numeric(5,4),
  suggested_price integer,                 -- 시스템 제안가
  final_price   integer NOT NULL,          -- ⭐ 실제 판매가
  margin        integer,                   -- final_price - purchase_cost (owner 전용)
```

### 3-12. `import_issue` — 이관 보정 대기 목록

1주차 데이터 이관에서 자동 처리가 안 된 건들을 **한 화면에 모아** 사장님이 정리한다.

```sql
CREATE TABLE import_issue (
  id         bigserial PRIMARY KEY,
  kind       text NOT NULL,       -- 'spec_parse'|'plate'|'dup_customer'|'maker'
  ref_table  text NOT NULL,
  ref_id     bigint,
  raw_value  text,
  suggestion text,                -- 시스템 제안값
  status     text NOT NULL DEFAULT '대기'
             CHECK (status IN ('대기','처리','무시')),
  resolved_by bigint REFERENCES app_user(id),
  resolved_at timestamptz
);
```

**예상 건수 (실측 기준):**

| 종류 | 건수 |
|---|---|
| 규격 파싱 실패 | 101 |
| 번호판 이상 | 11 |
| 중복 고객 후보 | 139 |
| 이름이 차량번호 | 3 |
| **합계** | **약 254건** |

> 254건을 한 화면에서 "확인/수정/무시" 버튼으로 처리한다. **반나절 작업이다.**
> 이걸 안 만들면 이상 데이터가 그대로 운영에 들어가고, 나중엔 못 찾는다.

## 5. 1주차 이관 순서

```
1. brand              (18종, 수동 작성)
2. vehicle_maker      (25종 + alias 48종 매핑, 수동 작성)
3. service_item       (69건, 엑셀 → qty_rule·rim 구간 수동 지정)   ← 반나절
4. product (타이어)   (10,691건, MARS 엑셀 + 규격 파서)           ← 자동
5. product (부품)     (약 265종, 재고 엑셀에서 신규 생성)          ← 반나절 (D-12)
6. customer           (2,603건, 연락처 엑셀 + 중복 판정)           ← 자동+확인
7. vehicle            (2,574건, 차량 엑셀 + 제조사 매핑)           ← 자동
8. stock_item (타이어)(미쉐린 57종 290본 + DOT 296본분)           ← ✅ 완전 자동
   ↳ 이 57종만 product.stock_tracked = true. 나머지는 false(⚪미등록)
9. stock_item (부품)  (약 265종, **수량 없이 `미확인`으로 생성**)   ← ✅ 자동
10. import_issue 정리 (254건 + DOT 이상 3건)                      ← 반나절
```

> **3번(service_item)이 손이 가장 많이 간다.** 69건에 `qty_rule`·인치 구간·국산수입을
> 일일이 지정해야 한다. 하지만 **한 번 해두면 견적이 평생 자동으로 계산된다.**

> **8번은 손댈 것이 없다.** 재고 코드가 MARS 품번과 100% 일치하므로
> 브랜드·규격·기표가가 자동으로 붙는다 (D-12).

> ⭐ **미쉐린 외 브랜드는 1주차에 넣지 않는다.** 사장님이 프로그램을 확인하신 뒤
> **2주차 입고 화면으로 직접 넣으신다** (D-12 6번). 그때까지 `⚪ 미등록`으로 표시되고,
> **견적은 정상적으로 나온다.** 재고 등록 여부가 판매를 막지 않는다.

> **9번은 수량을 버린다.** 부품 재고는 실물과 맞지 않으므로 **품목만 만들고
> 수량은 `미확인`으로 둔다.** 오일필터 시트 2개의 품목을 **합집합**으로 가져오면 된다.
> 어느 시트가 맞는지 고를 필요가 없어졌다.
