# 08. 시스템 아키텍처 확정

2단계 솔루션 아키텍트 산출물 | 2026-07-31

> 이 문서는 **"무엇으로 만들 것인가"** 를 확정한다.
> 비개발자가 읽어야 하므로, 각 결정마다 **현장에서 무엇이 달라지는지**를 먼저 쓴다.

---

## 1. 전체 그림

```
 ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
 │ 정비사 폰    │   │ 매장 태블릿  │   │ 사무실 PC    │
 │ (상담·견적)  │   │ (입출고 스캔)│   │ (사장님 전용)│
 └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
        └─────────────────┼─────────────────┘
                          │ HTTPS
                 ┌────────▼────────┐
                 │  웹 앱 (Next.js) │  ← 화면 + 서버 로직 한 몸
                 └────────┬────────┘
                          │
                 ┌────────▼────────┐
                 │  PostgreSQL      │  ← 모든 데이터
                 │  (서울 리전)      │
                 └─────────────────┘

  [수동 경로]  MARS 입력 대기열 화면 → 사람이 복사 → MARS
```

## 2. 확정 스택

| 영역 | 확정 | 이유 |
|---|---|---|
| 언어 | **TypeScript** | 오타·빠뜨린 값을 실행 전에 잡는다. 혼자 만들 때 특히 이득 |
| 프레임워크 | **Next.js 15 (App Router)** | 화면과 서버를 한 코드로. 폰·태블릿·PC 대응이 자동 |
| DB | **PostgreSQL 16** | D-06. 표준 SQL이라 나중에 어디로든 옮길 수 있다 |
| DB 접근 | **Drizzle ORM** | SQL에 가까워 나중에 순수 SQL로 떼어내기 쉽다 |
| 인증 | **Auth.js (자체 세션)** | 특정 업체 인증에 묶이지 않는다 |
| UI | **Tailwind + shadcn/ui** | 코드가 프로젝트 안에 들어온다. 버전 종속 없음 |
| 배포 | **Vercel** (앱) + **Supabase 서울 리전** (DB) | 관리 부담 0에 가깝고 월 0~5만원 |
| 표·엑셀 | **SheetJS** | 재고 엑셀 업로드, MARS 내보내기 읽기 |

### ⭐ 이식성 원칙 — 나중에 자체 서버로 옮길 수 있게

D-06에서 "향후 자체 서버 구축 가능성"을 말씀하셨다. 그래서 **묶이지 않는 방식**만 쓴다.

**지킬 것:**
1. **Supabase는 "그냥 PostgreSQL"로만 쓴다.** Auth·Storage·Realtime 등 고유 기능 **미사용**
2. **Vercel 전용 기능 미사용.** 표준 Node.js로 돌아가게 만든다
3. **처음부터 `docker-compose.yml`을 함께 만든다.** 이관이 "언젠가 할 일"이 아니라 상시 가능해야 한다

> 결과: 자체 서버로 옮길 때 **DB 덤프 + 컨테이너 실행**이면 끝난다. 코드 수정 없음.

## 3. 인증과 권한 — 장갑 낀 손을 전제로

### 문제

- 매장 태블릿은 **공용**이다. 누가 썼는지 남아야 하는데 매번 로그인은 못 한다
- 사장님 화면에는 **매입원가·마진**이 뜬다. 고객이 볼 수 있는 자리다
- 정비사는 장갑을 끼고 있다. 긴 비밀번호는 현실적이지 않다

### 확정 방식

```
최초 1회   아이디 + 비밀번호로 로그인 → 이 기기를 90일간 신뢰 등록
그 이후    화면 우측 상단에서 사람만 바꿈 → 4자리 PIN
사장님     PIN 필수 + 10분 미조작 시 자동 잠금 (마진이 보이므로)
```

- 기기를 잃어버리면 사장님이 관리 화면에서 **해당 기기 신뢰 해제** → 즉시 차단
- 모든 입출고·견적에 **누가 했는지** 기록된다 (`created_by`)

### 권한 2종

| | 사장님 (`owner`) | 정비사 (`tech`) |
|---|---|---|
| 기표가·판매가·견적 | ✅ | ✅ |
| 입고·출고·재고 조회 | ✅ | ✅ |
| **매입 할인율·매입원가·마진** | ✅ | ❌ |
| 할인율 **기본값 저장** (모델/브랜드 범위) | ✅ | ❌ (이번 건만 적용은 가능) |
| 마스터 수정·직원 관리·MARS 대기열 | ✅ | ❌ |

> 🔒 **중요 — 숨기는 방식**: 마진·매입원가는 **화면에서 가리는 게 아니라 서버 응답에서 아예 빼버린다.**
> 화면에서만 숨기면 브라우저 개발자도구로 다 보인다. 정비사 계정으로 요청하면
> **그 값이 전송조차 되지 않게** 한다. (D-05 6번 원칙의 실제 구현 방법)

## 4. 네트워크 — 정비소 와이파이는 끊긴다

정비소·창고는 전파가 약한 곳이 많다. 이걸 무시하면 "안 되는 시스템"이 된다.

### 확정 방침

| 상황 | 동작 |
|---|---|
| **조회** (재고·가격·차량) | 마지막에 본 데이터를 기기에 캐시 → **끊겨도 조회는 된다** |
| **입고·출고·견적 저장** | 온라인 필요. 실패 시 **화면 전체에 빨간 배너 + 재시도 버튼** |
| 재연결 | 자동 감지 → 배너 사라짐 |

> ❌ **오프라인 쓰기(나중에 자동 동기화)는 MVP에 넣지 않는다.**
> 재고는 실물과 맞아야 한다. 나중에 몰아서 반영하면 **두 사람이 같은 타이어를 판** 상태가
> 뒤늦게 드러난다. 그건 시스템 신뢰를 무너뜨린다. **차라리 그 자리에서 실패를 알린다.**

## 5. 바코드 입력 — 포커스를 신경 쓰지 않게

리더기는 **HID 키보드 모드**(스캔하면 글자가 타이핑됨 + Enter)로 쓴다.

**문제**: 보통은 입력창에 커서를 두어야 한다. 장갑 낀 손으로 매번 창을 누르는 건 부담이다.

**확정**: 화면 전체에서 키 입력을 감지한다.
- **아주 빠른 연속 입력 + Enter** 패턴 → 사람 타이핑이 아니라 **스캔으로 판정**
- 커서가 어디 있든 스캔이 먹는다. **그냥 쏘면 된다**
- 폰에는 리더기가 없으므로 **카메라 스캔**을 보조로 (같은 처리 경로로 들어감)

## 6. ⭐ 검색창은 하나만 둔다

이번 설계에서 **현장 속도를 가장 크게 바꾸는 결정**이다.

보통은 "차량번호 검색 / 고객 검색 / 규격 검색 / 바코드" 탭이 따로 있다.
정비사는 **무엇을 검색할지 먼저 고른 뒤** 입력해야 한다. 그 한 단계가 매번 든다.

**확정: 입력창 하나. 무엇을 넣었는지는 시스템이 알아서 판단한다.**

| 입력 예 | 자동 판정 | 결과 |
|---|---|---|
| `12가3456` | 차량번호 | 차량·고객·이력 |
| `3456` | 차량번호 뒷자리 | 후보 목록 |
| `01012345678` | 전화번호 | 고객 |
| `홍길동` / `한진택배` | 이름·메모 | 고객 (메모도 같이 검색 — D-10) |
| `225/45R17` `2254517` | 규격 | 재고 + 가격 |
| `8801234567890` | 바코드(13자리) | 상품 |

> 현장에서 달라지는 것: **고객이 뭐라고 말하든 그냥 받아친다.**
> "12가3456이요" 든 "홍길동인데요" 든 "225에 45짜리" 든 **같은 칸에 넣으면 된다.**

## 7. 개인정보 보호 (실명 2,603건 + 휴대폰 2,593건)

이제 실제 개인정보를 다루므로 지킬 선을 정해 둔다.

| 항목 | 방침 |
|---|---|
| 저장 위치 | **서울 리전**. 국외 이전 고지 문제를 만들지 않는다 |
| 접근 | 로그인한 직원만. 모든 조회에 세션 확인 |
| 전송 | HTTPS 전용 |
| 백업 | 일 1회 자동 + **주 1회 사장님 PC로 내려받기** (업체 폐업·계정 사고 대비) |
| 화면 노출 | 목록에서는 전화번호 **뒷 4자리만** (`010-****-5678`). 상세에서 전체 표시 |
| 퇴사 처리 | 계정 즉시 비활성 + 기기 신뢰 해제 |
| 문자 발송 | 수신거부 처리 필수. 광고성은 **[광고] 표기 + 무료수신거부번호** (법정 의무) |

> ⚠️ 내보낸 원본 엑셀은 **작업 폴더 밖으로 내보내지 않는다** (기존 원칙 유지).

## 8. 성능 — 지금 규모에서 걱정할 것과 아닌 것

| 데이터 | 규모 | 판단 |
|---|---|---|
| 상품 | 10,691 | 인덱스만 있으면 즉시 |
| 고객·차량 | 2,603 / 2,574 | 신경 쓸 규모 아님 |
| 재고 (1본=1행) | 연 ~10,000행 | 5년 써도 5만행. 문제없음 |
| 동시 사용자 | 최대 5명 | 문제없음 |

**필요한 인덱스만 정확히:**
- `vehicle(plate_no_normalized)` — 검색의 출입구
- `product(rim_inch, width, aspect_ratio)` — 규격 검색
- `product.fitment` — 부품 적용차종 부분검색 (pg_trgm)
- `customer(phone)` + `customer(name)` 한글 부분검색용 **pg_trgm**
- `stock_item(product_id, status)` — 재고 잔량 집계

> 결론: **규모 때문에 복잡한 구조를 미리 넣을 이유가 전혀 없다.**
> 캐시 서버, 검색엔진, 마이크로서비스 전부 불필요하다. 단순하게 간다.

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **정비사가 안 쓴다** (최대 리스크) | 검색창 1개·스캔 자동감지·부대비용 자동합산으로 "엑셀보다 빠름" 확보 |
| 재고가 실물과 어긋남 | 출고를 스캔으로만 → 4주차에 실사 1회로 기준점 맞춤 |
| 와이파이 끊김 | 조회는 캐시로 계속, 쓰기는 즉시 실패 알림 (4장) |
| MARS 누락 | 4주차 입력 대기열 + 3일 경과 경고 |
| 데이터 유실 | 일 1회 자동 백업 + 주 1회 로컬 다운로드 |
| 만든 사람만 아는 시스템 | 문서를 `docs/`에 계속 남김. 스택을 표준품으로만 구성 |
