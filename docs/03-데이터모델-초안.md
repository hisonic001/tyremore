# 03. 데이터 모델 초안

> ⚠️ **이 문서는 초안이며, `09-데이터모델-확정.md`로 대체되었다** (2026-07-31).
> 구현 시에는 **`09`를 기준**으로 할 것. 이 문서는 설계 경위 기록용으로만 남긴다.

---

## 1. 핵심 구조 한눈에

```
상품마스터(tire_product) ──┬── 재고(stock_item)  ← 1본당 1행
                           └── 가격규칙(price_rule)

고객(customer) ── 차량(vehicle) ──┬── 견적(quote) ── 견적항목(quote_item)
                                  ├── 보관(storage)      [2개월차]
                                  └── 작업이력(work_order) [3개월차]
```

---

## 2. 1차 오픈 대상 테이블

### tire_product — 상품 마스터
| 필드 | 설명 |
|---|---|
| id | PK |
| brand | 한국타이어, 금호, 미쉐린 … |
| pattern | K127, PS4 … |
| width / aspect_ratio / rim_inch | 225 / 45 / 17 |
| load_index / speed_rating | 94 / W |
| season | 사계절 / 여름 / 겨울 |
| barcode | 제조사 바코드 (EAN 등). **중복 가능** — 같은 상품이면 동일 |
| list_price | **기표가(정가)** — 견적 계산의 기준점 |
| is_active | 단종 여부 |

### stock_item — 재고 (1본 = 1행)
| 필드 | 설명 |
|---|---|
| id | PK. **시스템 자동 채번** (제조사 바코드로는 개별 식별 불가) |
| product_id | FK → tire_product |
| status | `재고` / `보관중` / `판매완료` / `반품` |
| dot | 제조주차. **선택 입력** (나중에 보완) |
| purchase_price | 매입가 — 마진 분석용 |
| received_at | 입고일 |
| location | 창고 위치 (자유 텍스트로 시작 → 2개월차에 랙·열·단 구조화) |

> 월 800본 기준 연 약 1만 행. 성능 문제 없음.

### customer — 고객 *(2026-07-31 개정 — 실제 MARS 구조 반영)*
| 필드 | 설명 |
|---|---|
| `id` | PK |
| `name` | **원문 그대로 보존.** `고태환[한진택배]` 같은 메모 포함 표기를 지우지 않는다 |
| `memo` | 이름 괄호 안 내용을 **복사**해 둠. 검색은 `name`·`memo` 둘 다 뒤진다 |
| `phone` | 휴대폰. 실데이터 **99.6% 보유** — 사실상 필수키 |
| `type` | `개인` / `법인·외상` ← MARS 회계 계정(D583/000000 vs 000010) 대응 |
| `grade` | 일반/단골/법인 등 — **MARS에 없음. 우리가 만드는 축** |
| `extra_discount_rate` | 등급별 추가 할인 |
| **`mars_contact_no`** | **MARS 「연락처」 번호 `C583-…`** ⭐ |
| `family_group_id` | 같은 전화번호를 쓰는 가족·법인 묶음 (병합 아님, 표시용) |

> ⚠️ **`mars_customer_no`(D583-…)는 쓰지 않는다.** 그건 회계 계정이지 사람이 아니다.
> 개인 고객 전원이 `D583/000000` 하나를 공유한다 — 식별자로 쓸 수 없다. **D-10 참조.**

> ❌ `email` 필드는 두지 않는다. 실데이터 **0건**이다.

### vehicle — 차량 *(2026-07-31 개정)*
| 필드 | 설명 | 실데이터 |
|---|---|---|
| `id` | PK | |
| `customer_id` | FK → customer | 매칭 100% |
| `plate_no` | 차량번호 — **조회의 출입구. 인덱스 필수** | 99.8% |
| `maker` | 제조사 — **정규화 코드로 저장** | 99.7% |
| `model` | 차종 | 96.1% |
| `year` | 연식 (MARS 「등록 날짜」 = 자동차 등록일) | 99.8% |
| `mileage` / `mileage_at` | 주행거리와 그 기준 시점 | 99.6% |
| `is_imported` | **국산/수입 구분 — 공임이 여기서 갈린다** | `maker`에서 파생 |
| `last_fitted_size` | 최근 장착 규격 | 판매 시 자동 기록 |
| `last_visit_at` | 최근 방문 | |
| `mars_vehicle_no` | MARS 차량번호 `V583-…` | |

> **외부 차량정보 API를 쓰지 않지만**(D-04) 제조사·모델·연식이 이미 99% 차 있다.
> 신규 차량만 최초 1회 사람이 채운다. 순정규격은 MARS에도 없으므로
> `last_fitted_size`("지난번에 뭘 끼웠나")로 대체한다 — 현장에서 더 자주 쓰는 정보다.

> ⭐ **`is_imported`가 중요하다.** 서비스 공임이 국산/수입으로 갈리므로(D-10),
> 이 값이 견적 금액을 바꾼다. `maker` 정규화 테이블에 국산/수입 플래그를 함께 둔다.

### service_item — 서비스·공임 *(1주차로 앞당김)*
MARS 「패스트핏 서비스 목록」 69건을 그대로 이관한다. **3개월차 → 1주차.**

| 필드 | 설명 |
|---|---|
| `mars_service_no` | `S001/1180` 등 — MARS 코드 그대로 |
| `name` | `휠타이어 교환 - 17인치 이하` |
| `price` | 공임 단가 (3건은 값 없음 → 건별 입력) |
| `category` | `90-SERVICE` 등 |
| `qty_rule` | ⭐ `per_unit`(본당) / **`per_2_units`(2개당)** / `per_job`(건당) |
| `rim_min` / `rim_max` | 인치 구간 — 규격에서 **자동 선택**용 |
| `for_imported` | 국산/수입 구분 (null이면 공통) |

> ⚠️ **`qty_rule`이 없으면 휠밸런스를 매번 절반만 청구한다.** "2개당" 요금이다.
> ⚠️ 인치 구간이 **교환은 17/18/21, 밸런스는 17/20/21**로 다르다. 사람이 고르게 하면 틀린다.

### MARS 연동 공통 필드 ⭐
**모든 거래성 테이블**(`quote`, `work_order`, 결제 기록 등)에 아래를 넣는다.
나중에 추가하려면 과거 데이터를 채울 수 없으므로 **처음부터** 넣는다.

| 필드 | 설명 |
|---|---|
| `mars_status` | `미전송` / `전송완료` / `보류` — **MARS 입력 대기열의 기준** |
| `mars_synced_at` | MARS 반영 시각 |
| `mars_ref_no` | MARS 측 문서번호 — 중복 전송 방지 및 사후 대조 |

> 원칙: **코드를 우리 마음대로 만들지 않는다. MARS 코드를 곁에 붙여둔다.**
> 고객번호·품번·결제구분은 MARS 값을 그대로 보관해야 대조가 가능하다.
> 상세는 `04-MARS-연동방안.md` 5장.

### price_rule — 가격 규칙
| 필드 | 설명 |
|---|---|
| scope | `브랜드` / `상품군` / `개별상품` |
| target | 적용 대상 (예: "한국타이어") |
| discount_rate | 기본 할인율 (예: 0.30) |
| priority | 규칙 충돌 시 우선순위 (좁은 범위가 이김) |

### quote / quote_item — 견적
견적 항목에 **계산 과정을 단계별로 저장**한다. 최종가만 남기면 마진 분석을 못 한다.

| 필드 | 설명 |
|---|---|
| list_price | 기표가 |
| product_discount_rate | 상품·브랜드 할인율 |
| customer_discount_rate | 고객 등급 할인율 |
| suggested_price | 시스템 제안가 |
| **final_price** | **현장에서 조정한 실제 판매가** |
| adjusted_by | 조정한 사람 (누가 얼마나 깎는지 파악용) |

> `suggested_price`와 `final_price`의 차이가 쌓이면
> **"가이드라인이 현실과 맞는가"** 를 데이터로 답할 수 있게 된다.

## 4. 설계 시 지킬 것

1. **삭제하지 않는다.** 재고·견적은 상태 변경으로 처리 (`판매완료` 등). 추적성 확보.
2. **가격은 스냅샷으로 저장한다.** 기표가가 나중에 바뀌어도 과거 견적은 그대로여야 한다.
3. **필수 입력을 최소화한다.** DOT, 차종, 연식은 전부 선택 항목. 나중에 채우게.
4. **차량번호는 정규화한다.** 공백·하이픈 제거 후 저장 (`12가3456`).
   단, **원문도 함께 보관**한다 — 이상치 11건(`강원61사65557` 구형식 등)이 있다.
5. **PostgreSQL 표준 기능만 쓴다.** 향후 자체 서버 이관 대비 (CLAUDE.md D-06).
6. **사람이 적어 넣은 표기를 시스템이 지우지 않는다.** 이름 속 메모 107건이 그 예다.
   정규화는 **검색 보조용 컬럼을 덧붙이는 방식**으로 하고, 원문은 남긴다.
