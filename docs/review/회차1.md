## 1. 고친 것 (5건)

### ① 계산서 ↔ 통장 잇기에 잠금이 없었다 — `recon-core.ts`

잔액을 **트랜잭션 밖에서** 읽고 삽입만 안에서 했다. 잇기가 두 번 눌리거나(휴대폰 더블탭·
느린 통신 재전송·「짝이 확실한 N건」과 손누름이 겹침) 하면 둘 다 「전액 남음」을 읽고
각자 연결을 넣어 **같은 돈이 두 번 잡힌다.** 절반만 들어온 돈으로 계산서가 「확인 완료」로
닫히는데 화면에는 아무 표시가 없다. `recon_match` 에 유니크 제약이 없어 DB 도 못 막는다.

- 읽기까지 전부 트랜잭션 안으로. `tax_invoice` → `cash_txn` **순서 고정** `FOR UPDATE` (교착 방지)
- 소진량은 정본 `cashUsedSql` 을 **같은 트랜잭션**으로 읽는다 (`cashUsedMap` 은 별도 연결이라 잠금이 뜻을 잃는다)
- 별명 학습은 트랜잭션 밖 — 학습 실패가 확정을 되돌리면 안 되고, 잠금을 오래 붙들면 안 된다
- 같은 위험을 `purchase-pay.payToSupplier` 는 이미 `FOR UPDATE OF pi` 로 막고 있었다. **계산서 연결에만 빠져 있었다**
- 검증: 실제 두 트랜잭션으로 1,643ms 뒤 `55P03` 차단 확인 (둘 다 ROLLBACK)

### ② 조용히 잘리는 `LIMIT` — `recon-data` · `tax-recon` · `deposit-tax` 9곳

`cashUsedMap` 의 `GROUP BY 1 LIMIT 20000` 이 제일 위험했다. 이 표는 **소진량 정본**이라
빠진 줄은 「0원 썼음 = 전액 남아 있음」으로 읽힌다. 한도를 넘는 순간 **이미 다 쓴 통장 줄이
후보에 되살아나 같은 돈이 두 계산서에 이어진다.** 오류도 경고도 안 난다.
게다가 이 표는 자료가 늘어서가 아니라 **앱을 쓸수록** 커진다.

해제: `cashUsedMap`(20000) · `party_alias`(10000×6곳) · 열린 마이너스 계산서 `negs`(200×2곳).
전부 WHERE 나 표 크기가 이미 범위를 묶고 있어 한도가 애초에 필요 없었다.

### ③ 「대기」를 현황·마감이 계속 셌다 — `tax-recon.ts`

「아직 안 들어옴 — 다음 달로」를 만든 이유가 *"그래야 달이 닫힌다"* 였는데, 정작
마감 체크리스트(`month-close.ts` — `ok: taxN === 0`)와 현황 카드가 쓰는 `taxOpenCounts` 는
`recon_status <> '무시'` 를 손으로 따로 적고 있어 **대기를 셌다.** 미뤄도 달이 안 닫힌다.

🔴 **감사 C1 → 감사 N1 → 이번**, 「첫 화면 ↔ 탭 숫자 불일치」의 **세 번째 재발**이다.
규칙을 복사하지 않고 `LIVE` 를 **모듈 정본으로 올려** 두 곳이 같은 것을 쓰게 했다.

### ④ 자동 점검이 0개였다 — `src/lib/money-rules.test.ts` 신설 (30개)

코드 주석의 감사 번호(F1~F21 · G1~G11 · N1~N9 · R2~R9)가 사실상 테스트 대장이었다.
사장님이 화면을 안 보셔도 앱이 **스스로 돈을 잇는 근거** 넷을 지킨다:
금액 조합 · 수수료 허용 오차 · 상대 이름 ★≈ 등급 · 「짝이 확실한 N건」.

시험값은 지어내지 않았다 — 전부 주석에 남은 실제 사례(위즈오토·유일이엔티·진양윤활유·
록산기전·양양현대자동차·타이어프로 속초점·늘푸른요양원).
새 도구 설치 없음(이미 있는 `tsx` + Node 내장). **DB 에 접속하지 않는다.**

### ⑤ 입금 화면이 질의를 100개 넘게 던졌다 + 창이 좁았다 — `deposit-tax.ts`

`transferSalesMissing` 이 **판매 한 건마다** 통장을 따로 뒤졌다. 접속 자리가 3개뿐이라
(`src/db` `max: 3`) 화면 하나가 자리를 오래 붙들면 앱 전체가 멎는다 — 2026-08-05 ·
08-11 에 실제로 겪은 「좀비 질의 → 풀 만석」 과 같은 길이다.

- 한 번 긁어 판매마다 JS 에서 고른다 → 2026-08 기준 **질의 20 → 2회, 1,051 → 306ms**
- **창을 ±10일 → ±90일로 넓혔다** (사장님 지적: *"몇 달 후에 입금시키는 경우도 있음"*)
  실측: 2026-06 은 못 맞춘 판매 26건 중 ±10일이면 후보가 뜨는 게 **1건뿐**인데 ±90일이면 12건
- 판매당 400개 뚜껑도 없앴다 — 그 400개를 「날짜 가까운 순」으로 골라서, 창만 넓히고 두면
  **정작 멀리 있는(늦게 들어온) 입금이 먼저 잘려** 넓힌 뜻이 사라진다
- 화면 대조(실자료 3개월): 판매 건수 동일, **사라진 후보 0건**, 늘어난 것만 5건

## 3. 재발 방지 — 이제 명령 두 개로 확인된다

```bash
npm test     # 돈 계산 규칙 30개 (DB 없이 · 1초)
npm run check # 실제 자료로 4가지 점검 (아래)
```

| 스크립트 | 무엇을 지키나 | 지금 값 |
|---|---|---|
| `check-money-links.ts` | ①의 재발 — 같은 돈이 두 번 잡힌 자국 | 중복 0 · 초과 배분 0 ✓ |
| `check-limits.ts` | ②의 재발 — 목록이 조용히 잘리는 것 | 소진량 199 · 별명 92 · 미지급 31/400 ✓ |
| `check-counts-match.ts` | ③의 재발 — 화면마다 숫자가 갈라지는 것 | 5개 달 × 4항목 전부 일치 ✓ |
| `check-query-load.ts` | ⑤의 재발 — 질의가 자료 따라 느는 것 | 입금 화면 18 고정 ✓ |

**설계 원칙 두 가지** (다음 회차도 이렇게 유지할 것):

1. **절대 개수가 아니라 「자료가 늘면 같이 늘어나느냐」를 본다.** 질의 18개가 늘 18개면 괜찮다.
   자료량이 크게 다른 4개 달(2026-08 · 06 · 01 · 2025-06)을 돌려 흔들리는지 본다.
2. **「아는 것」과 「새것」을 가른다.** 알고도 놔둔 것이 늘 빨간불이면 잔소리가 되어
   정작 새로 생긴 것을 못 본다. `known: true` 는 ⚠ 를 띄우되 **실패로 세지 않는다**(exit 0).

## 4. 다음 회차가 미리 알아야 할 것

### ⚠ 지금 켜져 있는 경고 — 이게 정상이다

`npm run check` 를 돌리면 아래 둘이 ⚠ 로 뜬다. **고장이 아니라 알고 놔둔 것이다.**

1. **계산서 돈 확인(매입)이 자료 따라 는다 — 이게 다음 병목이다.**
   실측: **기본 10질의 + 월정산 상대 1곳당 4질의.** (34 / 38 / 54 / 46 = 10 + 4×상대수)
   지금 상대가 6~11곳이라 34~54회. **20곳이 되면 90회**라 접속 자리 3개로는 위험하다.
   위치: `taxCashData` 의 `for (const mr of monthlyRules)` — 상대마다
   `inv 집계` + `partyStrictNames` + `partyMonthlyCash` 를 따로 돈다.
   ⑤와 **똑같은 모양**이니 같은 방법으로 고칠 수 있다(한 번 긁어 JS 에서 나누기).
2. **±90일 창을 더 넓히면 몇 건 더 잡힌다** (2026-06 +1 · 2026-01 +2).
   이 정도는 정상이다 — 넓힐수록 「금액만 같은」 엉뚱한 후보가 늘 뿐이다.
   **한 달에 5건 넘게** 더 잡히면 그때 `deposit-tax.ts` 의 `WIN` 을 다시 본다.

### 손대지 않은 채 남아 있는 뿌리 문제

- **`recon_match` 에 유니크 제약도 FK 도 없다.** ①·F10·F5 가 전부 여기서 나온다.
  🔴 다만 **그냥 제약을 걸면 실패한다** — 이체 수수료 잔돈 흡수 13행이 정확히
  `(kind, src, ref)` 중복 모양이다. 그 13행을 어떻게 다룰지부터 정해야 한다
  (예: `method='조정'` 을 제약에서 빼거나, ref_table 을 `adjust` 로 바꾸거나)
- **`recon_match.amount` 가 `integer`** — 21.47억 상한. 지금 건별 수천만원대라 여유는 크지만,
  연·분기 합계 계산서를 한 줄로 넣게 되면 닿는 자리
- **`kind` 마다 `cash_txn` 이 src 인지 ref 인지 뒤집힌다** (`recon-data.ts:932-938` 이 그걸 주석으로 남길 정도).
  모든 소비처가 방향을 외워야 한다 — 헬퍼로 감추면 이 계열이 통째로 줄어든다
